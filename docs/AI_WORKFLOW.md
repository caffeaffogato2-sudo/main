# AI Workflow

## 1. Repository policy

- 1案件 = 1リポジトリとする。
- このリポジトリは共通入口であり、案件本体を格納しない。
- 各案件リポジトリの `main` を正本とする。
- 改修は原則 `work/<task>` ブランチで行い、Pull Request を経由して `main` へ反映する。
- AI名をブランチ名やフォルダ名に使わない。

## 2. Tool selection policy

通常作業は ChatGPT Chat を基本とする。

### ChatGPT Chat

主に以下を担当する。

- 要求整理
- GitHub現状確認
- 仕様・文書・コード分析
- 影響分析
- 改善計画
- 小規模変更
- Pull Request / 差分レビュー
- 回帰レビュー
- 最終品質確認
- Codex / Claude Code への作業範囲定義

### Codex

ChatGPT Chat で実施すると非効率な場合に限定して利用する。

- 大規模コード実装
- 多数ファイルにまたがるコード変更
- リファクタリング
- テストコードの大量追加
- 繰り返し実行を伴うコード修正

### Claude Code

ローカル環境または実行環境が必要な場合に限定して利用する。

- Windows依存確認
- PowerShell / cmd 実行
- ローカルアプリ実行
- Excel実機確認
- 大量ファイル処理
- OS依存エラー調査
- 複雑なE2E検証

## 3. Token-efficient collaboration

- ChatGPT Chat で完結できる作業を Codex / Claude Code へ重複依頼しない。
- AI間で会話全文を引き継がない。
- AI間のI/Fは GitHub 上の要求、設計、対象ファイル、差分、Pull Request、検証結果とする。
- リポジトリ全体を毎回読み直さず、対象ファイル・差分・必要な関連ファイルを優先する。
- 多重AI確認は同一作業の重複ではなく、異なる観点の独立確認に使う。

## 4. Standard workflow

1. 現在の `main` と対象範囲を確認する。
2. 目的、変更対象、変更内容、変更しない範囲、検証方法を明確にする。
3. `work/<task>` ブランチで作業する。
4. 要求範囲外の変更を行わない。
5. 適用可能な検証を実施する。
6. `main` との差分を確認する。
7. 変更ファイル、実施した検証、未解決事項を記録する。
8. Pull Request を作成する。
9. 作成者とは異なる観点で差分レビューする。
10. 人の承認後に `main` へ反映する。

## 5. Quality rules

- 未実施の検証を PASS と扱わない。
- 推測だけで既存仕様を変更しない。
- 要求外のリファクタリングを混在させない。
- `main` への直接変更は、空リポジトリ初期化等の明示された例外を除き原則禁止する。
- force push や不要な履歴改変を行わない。
- 他AIが作業中のブランチを無断で上書きしない。
